# 案例：一个自绘页面，两个包分别看到了什么

> 目标页面：`com.demo.canvas/.MainActivity`（整页 Canvas 绘制，无原生控件）

## lint 看到的（只读采集）

```
nodes=8  interactive=0  unlabeled=0  undersized=0  invisible=0  zero=False
无可操作节点页面（疑似自绘/图片化，需截图确认）
```

含义：**8 个节点全是装饰**（窗口、标题栏、根布局），没有任何可交互控件。
屏幕阅读器在这页上读不到按钮，文字型自动化也找不到锚点。

这是 26 页样本里唯一命中的一页（3.8%）。

## engine 遇到的（文字通道）

`find_text()` 在这页上返回 not found —— 不是"找得慢"，是**树里根本没有**。

## engine 的视觉通道（截图哈希）

```
1  home           OK    回到桌面
2  launch         OK    com.demo.canvas/.MainActivity
3  assert_changed OK    画面已变化
4  assert_stable  OK    连续两帧一致
```

含义：即使没有任何可读节点，"启动动作是否生效""画面是否稳定"仍然可以用
截图哈希判断——**动作可验证，但不可寻址**。

## 视觉定位原型能不能用（`engine/vision.py`）

对同一张截图做连通域检测（页面下部、非白非黑、有饱和度的像素）：

```
1) 定位到 4 个可点区域：
   #0 (172,2143) 203x158 selected=False
   #1 (416,2143) 203x158 selected=False
   #2 (660,2143) 203x158 selected=False
   #3 (904,2143) 203x158 selected=True
```

**定位成功**：A/B/C/D 四个圆钮全部找到，且正确判断出 D 是选中态（蓝色）。

**但点击无效**：`MockExerciseActivity` 是**只渲染、不处理触摸**的（源码里没有 `onTouchEvent`）。
实测点 (172,2143) 后整页只有状态栏变了 675 个像素，A 区域颜色完全没变。

### 于是自己写了一个"会响应"的夹具

`engine/fixture/`（包名 `com.demo.canvas`，12 KB，单文件自绘 + `onTouchEvent`）。
同一个页面结构，但会处理触摸。实测：

```
无障碍树节点数 = 5              ← 只有窗口/根布局，没有任何控件

1) 定位到 4 个可点区域：
   #0 (154,2022) 204x204 selected=False
   #1 (411,2022) 204x204 selected=False
   #2 (668,2022) 204x204 selected=False
   #3 (925,2022) 204x204 selected=True
2) 当前选中: [3]；准备点击 #0 (154,2022)
3) 点击后重定位: 4 个区域，选中=[0]
4) 选中态转移: 成功 ✅
```

**完整闭环**：读图定位 → 判断状态 → 点击 → 再读图验证状态转移，全程零无障碍节点。

### 换一种"不依赖颜色"的方法

连通域依赖"选中态是蓝色"这个先验。真实界面里更通用的做法是**模板匹配**：
把"选中样式"裁出来当模板，点击后看这个模板跑到哪去了。

```
1) 取『选中态』作模板：来自 #2 (668,2022) 204x204
2) 点击 #0 (154,2022)
3) 模板匹配：score=0.999 位置=(154,2022)
4) 距离 0px（阈值 40），得分阈值 0.90 → 通过 ✅
```

第一版分数只有 0.882：模板里含字母"A"，目标处变成了"B"，字面差异把分数拉下来了。
把模板中间 52% 的方形区域屏蔽掉、只比对圆环后，分数升到 **0.999**。
**这条经验通用**：比对"样式"时要先想清楚哪些像素与样式无关。

得分只有 0.882 而不是 1.0，是因为模板里含字母"A"，点到 B 后字母变了——
**这恰好说明匹配对内容差异是敏感的**，可用来判断"是不是同一个控件"。

### 第三条通道：OCR 读出文字并点击

视觉能定位"形状"，但读不出"写的是什么"。补上 OCR（Windows 自带引擎，zh-Hans-CN）：

```
1) OCR 找到「C」：包围盒 (636,1967,72,93)，中心 (672,2013)
2) 已点击 (672,2013)
3) 视觉验证：选中态=[2]（轮询 1 次，期望 [2]）
4) 通过 ✅
```

**三通道分工**：

| 通道 | 能做什么 | 代价 |
|---|---|---|
| 无障碍文本 | 最准、最便宜 | WebView/Canvas 上可能完全没有 |
| OCR | 读得出画面上写的字，给包围盒 | ~0.7s/次，字形差时有误差 |
| 视觉（形状/哈希） | 定位规则形状、判断状态与变化 | 读不出语义 |

配合起来就是：**OCR 找"点哪个"，视觉验证"点中了没"**。

### 一个被真机打出来的坑

第一版闭环在点击后 `sleep 0.8s` 再截图，单跑通过、连跑偶发失败。
改成**轮询到"选中态确实变了"**（最多 4 秒、每 0.3 秒一次）后，连跑两次都稳定。
这和 lint 那边"不许固定 sleep"是同一条纪律——**固定延时是最容易埋雷的写法**。

## 用能响应的页面验证"点击 + 视觉验证"

```
1  home           OK    回到桌面
2  launch         OK    com.vendor.calculator
3  tap_text       OK    点击 (418,1671) 5
4  assert_changed OK    画面已变化
```

点击用文字定位（计算器有无障碍节点），**验证用截图哈希**——
说明"动作有没有生效"可以不依赖无障碍树来判断。

## 结论

| 能力 | 文字通道 | 视觉通道 |
|---|---|---|
| 找到"按钮" | ❌ 不存在 | 需要元素检测/OCR（本 demo 未做） |
| 判断动作生效 | ❌ | ✅ 哈希变化 |
| 判断加载完成 | ❌ | ✅ 连续两帧一致 |

所以对一个自绘页面：
- **能不能操作**：需要视觉定位（超出本 demo 范围，是 M3 的方向）
- **有没有操作成功**：现在就能判断
